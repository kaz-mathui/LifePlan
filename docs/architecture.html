🏠 LifePlan ってどんなアプリ？

ひとことで言うと

未来の家計をシミュレーションし、グラフで可視化する Webアプリ。

👤 ユーザーから見ると

  • ブラウザでアクセス（PC/スマホ）
  • Google アカウントでログイン
  • 収入・支出・資産を入力
  • 未来の資産推移をグラフで確認

💻 技術的に何が動いてる？

  • frontend React (CRA) + Chart.js
  • backend Node.js + Express
  • DB Firestore（NoSQL）
  • 認証 Firebase Authentication
  • インフラ Google Cloud Run

💡 個人開発プロジェクト。コストは月数百円〜数千円レベル（min-instances=0 のおかげ）。

🚶 リクエストの旅

Slide 4 の全体像を 時系列 で追います。例として「収入を保存」ボタンを押す動作。

1
URL を開く

Cloud Run の frontend が HTML / JS / CSS を返す。

2
React アプリ起動

Firebase Auth にログイン状態を問い合わせ。

3
Google でログイン

Firebase Auth が IDトークン (JWT) を発行。以降のAPI呼び出しに添える。

4
「収入を保存」を押す

React が POST /api/income を backend に送信。ヘッダに IDトークン付き。

5
backend が IDトークンを検証

Firebase Admin SDK が Google の公開鍵（自動取得）でトークンの署名を検証。改ざんされてないか・誰のものかが分かる。

6
Firestore に保存

users/{uid}/income に書き込み。
Admin SDK の認証には SAキー（Secret Manager 経由で注入） を使用。

7
200 OK を返す

React が UI を更新して「保存しました」を表示。

📌 現状の過渡期構成

CI/CD は WIF でキーレスだが、backend の Firestore 接続には SA キー JSON を使用中。将来的には Cloud Run ランタイム SA に Firestore 権限を付与する ADC 方式 に置き換えると、アプリ側からも JSON キーが消える。

🔄 無停止デプロイ

新リビジョンを立ち上げてから古いのを止める方式。ユーザーが見ているページは切れない。

💸 アイドル時 0 円

min-instances=0 のためアクセスがなければインスタンス0。固定費ゼロで個人開発の友。

⚠️ コールドスタートあり

アイドルからの初回アクセスは 1〜3秒の起動待ちが発生。レイテンシ重視なら min-instances=1（月数百円〜）。

🔐 WIF — キーレス認証の仕組み

Workload Identity Federation（ワークロード・アイデンティティ・フェデレーション）。 CI/CD が GCP にアクセスするときに、JSONキーを使わない仕組み。

例え話で理解する

🔑 昔のやり方（SA キー JSON）

家の合鍵を1本作って渡す。

  • 持ってる人は誰でも家に入れる
  • なくしたら大事故 → 鍵交換
  • 定期的にローテーション必要
🪪 WIF のやり方

受付（WIF Provider）で身分証 → 一時パスに交換。

  • 受付は kaz-mathui/LifePlan リポからの提示しか受け付けない
  • 一時パスは 1時間で失効
  • JSON キーがそもそも存在しない

💡 OIDC の本質は「リポジトリ・ブランチ・ワークフロー等のクレーム（主張）を含む JWT」。WIF Provider 側で「どのリポからの提示なら通すか」を厳密に絞るのがセキュリティの要。

実際の流れ

sequenceDiagram autonumber participant GA as GitHub Actions participant OIDC as GitHub OIDC participant Pro as WIF Provider participant STS as GCP STS participant CR as Cloud Run GA->>OIDC: 身分証ください OIDC-->>GA: JWT リポ名 ブランチ等を含む GA->>Pro: この身分証で GCP 入れますか Pro->>Pro: リポジトリ条件チェック Pro->>STS: OK SA impersonated トークン発行 STS-->>GA: アクセストークン 有効1時間 GA->>CR: そのトークンでデプロイ実行 Note over GA,CR: ジョブ終了、トークン自動失効
⚠️ アンチパターン

attribute condition を緩く repository_owner だけにすると、同じ owner の他リポからも同じトークンが取得できてしまう。repository か google.subject を必ず条件に入れること。

💡 ポイント: もし GitHub Actions のログがどこかに漏れても、その時には既にトークンが失効している。被害が限定的。

🤔 なぜこの技術を選んだのか

☁️ なぜ Cloud Run？

  • サーバ管理不要。OS パッチ・スケーリング全部おまかせ
  • 使った分だけ課金。min=0 でアイドル時0円
  • HTTPS 自動。証明書管理も自動
  • Docker さえあれば動く。コンテナ部分のポータビリティはある

🔥 なぜ Firebase？

個人開発で「認証 + DB を最短で揃える」なら現状ほぼ一強。

  • Google ログイン即実装、自前管理不要
  • Firestore はリアルタイム同期可
  • 無料枠が広く個人利用ならほぼ課金されない

⚠️ Firestore と Auth は GCP 固有。ロックインは強い。それを受け入れる代わりに開発速度を取る選択。

🔐 なぜ WIF？

  • JSON キーが存在しない → 漏洩リスク・ローテ作業ゼロ
  • Google が公式に推奨しており、新規構築時の第一候補になりつつある
  • リポジトリ条件で第三者からの偽装を防御
  • 失敗時のトークン失効も自動

⚛️ 補足: React (CRA) について

情報量が多く Firebase の React SDK も充実。ただし CRA 自体は開発が止まりつつあるため、将来的には Vite への移行も検討余地あり。

📖 用語集

このスライドで出てきた言葉を整理。同僚との会話で「これ何？」と聞かれたら答えられるレベルで覚えておくと吉。

用語意味
Cloud RunGoogleのサーバレスコンテナ実行環境。Dockerイメージを渡すと自動でHTTPS付きで動く
Artifact RegistryGCPの Docker イメージ保管庫。AWS でいう ECR
FirestoreFirebaseのNoSQLデータベース。JSON っぽい形でデータを保存できる
Firebase AuthGoogleが提供する認証サービス。Googleログイン・メール認証等を簡単に実装できる
Service Account (SA)「人間じゃないユーザー」。アプリやCI/CDがGCPを操作する時に使うID
WIFWorkload Identity Federation。外部サービス（GitHub等）の身分証でGCPに入れる仕組み
OIDCOpenID Connect。「私は誰々です」を証明する身分証の標準規格
JWTJSON Web Token。署名付きで改ざん検知ができる身分証データ。中身は base64 エンコードなので誰でも読める（暗号化ではない）→ 機密情報は入れない
impersonate「このSAとして振る舞ってよし」という権限委譲
ADCApplication Default Credentials。Cloud Run などのGCP上で動くアプリが、自動でランタイムSAの権限を使う仕組み。JSONキー不要
Docker「アプリと環境を1つの箱にまとめる」技術。Cloud Runはこの箱を動かす
min-instancesCloud Runで「常に何台動かしておくか」の設定。0にするとアイドル時は0台で課金されない（代わりにコールドスタートあり）
コールドスタートCloud Run でインスタンス数0から起動するときの初回アクセス遅延（Node.js+Firebaseで1〜3秒）
monorepo1つのリポジトリに複数のアプリ（frontend/backend）をまとめる構成

🎯 まとめ & 次に学ぶといいこと

このアプリで覚えてほしい3つ

☁️ コンテナ型サーバレスは個人開発に合う

Cloud Run の min=0 でアイドル時0円。FaaS と違って言語/ランタイム自由。

🔥 マネージドDBは時間を買う

Firebase Auth + Firestore で認証〜永続化が一気通貫。ロックインの代償と引き換え。

🔐 WIF でキーレス CI/CD

JSONキーをリポに置く構成を WIF に置き換えると、漏洩リスクとローテ作業がなくなる。

もっと深く知るためのキーワード

  • Cloud Run 第二世代実行環境 — gen2 ランタイムでより高速
  • Cloud Run 同時実行数（concurrency） — 1インスタンスで何リクエスト捌くか
  • Firestore セキュリティルール — クライアントから直接アクセス時の権限制御
  • Cloud Build / Cloud Deploy — GitHub Actions の代わりにGCP内で完結させる選択肢
  • VPC コネクタ — Cloud Run から VPC 内リソースにアクセスする方法
  • Workload Identity（GKE版） — Kubernetes ポッドへの応用
